# Issue 18 acceptance audit

This audit reads the original seven acceptance criteria in [#18](https://github.com/rkttu/vscode-csharp-autobuild/issues/18) against merged code through [PR #43](https://github.com/rkttu/vscode-csharp-autobuild/pull/43), merge `32eae02d4c9594be42d85f93fa1e38b079184867`, and the new [host-loss observations](README.md). The primary host-loss control passes; its separate compiler regression fails and remains retained. This distinguishes lifecycle implementation from the installed-editor qualification owned by [#15](https://github.com/rkttu/vscode-csharp-autobuild/issues/15). It does not close #18 or qualify a release.

## Qualification scope already owned elsewhere

The [support contract](../../stability-contract.md) was defined by closed [#14](https://github.com/rkttu/vscode-csharp-autobuild/issues/14); it explicitly leaves qualification ungranted. #15 owns exact target/input pinning, native Windows/macOS VSCodium measurements, numeric phase budgets, no-folder/folder and saved/dirty Console/Web/project scenarios, breakpoint/evaluation/stepping, separate command/menu/F5 inputs, ten cycles in each of two fresh profiles, language-service readiness, CI gating and first-failure retention. Routing is #16, context/SDK transitions are #17, explicit HTTPS/certificate policy is #20, and release/public-readback qualification is #21.

These are substantial open stabilization work, but they do not require #18 to grow a new native control for every already covered unit interleaving. No installed control in this series grants native macOS, physical F5/menu, unconstrained throughput, arbitrary descendants or release qualification. Existing offline language-service restore failures remain visible qualification limitations, not unexplained errors erased by a green lifecycle rerun.

## Bounded remaining path

1. The first actual abrupt active-host-loss control is complete in an isolated production-mode extension host. This describes the editor's extension mode, not a deployed production environment. `n01` verifies old host 7724 replaced by 101472 under editor 97568, independently samples old adapter 100536/debuggee 33244/port 51232 release, preserves unknown output/guard bytes, and proves three dirty callers use one fresh native launch and clean its output. The initial snapshot is before explicit activation; automatic product activation may already have run. No additional native interleaving is required merely to repeat this passing observation.
2. Preserve and investigate the original failed `c01` regression before accepting this evidence change. Its actual compiler error handling and corrected A launch pass, but B receives a DAP pause, stops, and receives no continue before HTTP timeout. Do not erase that first failure with an automatic resume/rerun or infer the higher-level pause caller. Previously passing B-preservation evidence remains historical evidence; it does not turn this failed attempt green. Unknown old host-loss output must also remain intact; its conservative preservation is separate from this compiler regression failure.
3. Keep the sixth criterion explicitly open as one focused foreground-await/deferred-drain work item. Define machine-owned versus user/editor-owned waits, and specify what foreground completion can guarantee while underlying work remains unresolved. Package-owned cancellation must not turn an uncertain live output into a terminal receipt or drop observation of a late session.
4. Implement and test that policy with never-settling and late-resolving/rejecting save/SDK/build/Web/handoff/cleanup providers where applicable: foreground timeout/cancel, original error retention, safe ownership, no downstream launch from an expired generation, unrelated-session preservation and corrected retry. A `Promise.race` alone cannot cancel underlying I/O or authorize deletion. Non-cooperative OS/event-loop blocking needs an explicit supported boundary rather than a false hard-time guarantee.
5. #15 then calibrates and versions numeric budgets for the accepted boundaries and performs the full installed matrix. Close #18 only after its remaining implementation criterion is met, or after an explicit linked scope/ownership revision is made consistently in #18 and the contract. Do not silently mark the original total-phase criterion complete merely because the host-loss control passes.

A small first implementation slice for criterion six is the known-terminal cleanup retry that a later fresh command currently awaits (`retryFailedCleanup` in `runtime.cjs`). Observe that already authorized cleanup in the background while retaining its `cleanupInFlight` and `ownedOutputs` ownership until actual settlement, including late errors. A fresh command can then use a distinct output. Test unresolved/late-resolving/late-rejecting cleanup and prevent duplicate deletion or early ownership release. Do not put a timeout inside `cleanup()` whose `finally` would release drain ownership early. Current-run failure cleanup, user-owned save/certificate dialogs and editor-owned handoff require subsequent explicit policies; this proposed first slice does not solve the whole criterion.

The current [preparation-deadline evidence](../preparation-deadline-2026-11-04/README.md) already explains that abort requests wait for direct-child close and that a non-cooperative process or blocked filesystem operation can exceed five minutes. That documented limitation is useful evidence for the next design decision; it is not proof that the original total-phase-bound criterion has been implemented.
