## Original acceptance criteria

The following seven unchecked criteria reproduce #18's existing wording. They are not a new completed checklist.

- [ ] Failure or cancellation at each stage releases pending work and permits a corrected same-file run without dismissing earlier notifications or restarting the editor.
- [ ] Inject cancellation before/during/after debugger handoff; any session started after cancellation is stopped safely without affecting unrelated sessions.
- [ ] Report false launch results with actionable phase-specific diagnostics; expected user cancellation is distinguished from a fault.
- [ ] Verify real build children, debug sessions, Web ports and owned temporary outputs are cleaned; transient cleanup failures retain a safe bounded retry mechanism.
- [ ] Define conservative cleanup for interrupted/reloaded hosts using explicit ownership metadata, with tests proving unrelated paths are preserved.
- [ ] Bound total operation phases and show progress/durations so slow SDK evaluation is distinguishable from a blocked command.
- [ ] Exercise process/start failures, repeated F5, concurrent separate files, disposal and crash/reload recovery in the installed-editor harness.

## State and ownership distinctions

The [current phase/ownership table](../stability-contract.md#implemented-foreground-policies-and-ownership) describes implemented guardrails separately from qualification. Four default five-minute budgets do not establish a five-minute whole-operation limit, a calibrated performance threshold or a finite actual-drain guarantee.

A foreground task can select failure, cancellation or timeout while its underlying workflow remains observed. That separation depends on a responsive event loop and the editor delivering the task callback/outcome normally. It cannot impose finite completion on an arbitrary editor provider that never calls the callback or permanently withholds its result. The source gate is released only after both the foreground and logical workflow settle. A still-pending write-capable save/provider/child therefore prevents competing same-file work. Known-terminal cleanup can continue in the background while a fresh run uses distinct output.

Owned debugger handoff has a different safe retry boundary: its cancellation race can settle the workflow while the original editor API request remains in `pendingStarts`. A fresh same-file run can then use another output directory. The old request and any exact late session remain tracked independently; only trusted terminal evidence authorizes its cleanup. API acceptance (`true`), an exact `onDidStartDebugSession` observation, debugger readiness and terminal evidence are separate facts. Neither API acceptance nor a start event proves breakpoint binding or initialized debuggee readiness. Missing events preserve uncertainty rather than establish process absence.

Existing cleanup paths include known pre-handoff failure or a declined/rejected start without a captured session, exact owned editor termination, and the narrow disposal-only fallback requiring a valid debuggee exit followed by non-restarting termination in the same captured session's tracker. Stop acknowledgement alone is insufficient. Exact termination can authorize output cleanup while the original API promise is still pending; that pending API independently retains disposal ownership. Validated terminal receipts govern later recovery, not arbitrary unmarked output.

Two other boundaries remain explicit. Pure profile input reads use `Promise.all`: one failure can finish logical Web preparation while a sibling input read remains observed. Its late result cannot resume parsing, SDK work or output use; this is not a guarantee that every OS read has settled. Also, dirty included-project files still save before classification, but once the existing selected-project debug command is dispatched its editor-owned completion is awaited without a file-app session handle or new file-app deadline.

The Web active-time budget pauses during certificate consent and trust, then resumes its remaining time for verification. The existing individual .NET process timeout still applies during trust. Pausing the shared budget is not a promise of unlimited OS trust, OS preemption or guaranteed process termination.

## Unchanged qualification and unresolved failures

The [support contract](../stability-contract.md) remains the qualification authority: native Windows ARM64 and macOS ARM64 VSCodium with stable, serviced .NET 10; exact pinned inputs; required scenarios and separate command/menu/F5 routes; and first-failure preservation. For each required scenario and target, each of two independently created profiles must run ten consecutive cycles. Single controls from different source refs, candidates, profiles or targets cannot be combined into that required consecutive-pass sequence for one candidate. This proposal changes none of those targets, protocols or thresholds and does not qualify any combination.

[#15](https://github.com/rkttu/vscode-csharp-autobuild/issues/15) retains measurement, calibration and qualification gates. [#16](https://github.com/rkttu/vscode-csharp-autobuild/issues/16) retains entry integration/routing and actual input parity; [#17](https://github.com/rkttu/vscode-csharp-autobuild/issues/17) retains context transition/recovery; [#20](https://github.com/rkttu/vscode-csharp-autobuild/issues/20) retains HTTP/Slim/explicit HTTPS policy and qualification. Some remaining work in those issues can require implementation. [#21](https://github.com/rkttu/vscode-csharp-autobuild/issues/21) remains the release exit gate. Naming those owners neither waives AC7 nor silently transfers a requirement out of #18.

[#45](https://github.com/rkttu/vscode-csharp-autobuild/issues/45) remains an unresolved, separately tracked original compiler-control `c01` failure: B received an unexplained Pause. The [review record](pr44-review-2026-11-08/README.md) preserves the original failure and the later non-reproduction separately. A green rerun, additional trace output or this proposal does not identify the actor, fix that failure or establish an all-pass qualification. No automatic Continue, inferred cleanup or “by design” relabelling is an acceptable substitute for disposition.
